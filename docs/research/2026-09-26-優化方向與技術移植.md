# 優化方向與技術移植

本文件承接同日的端到端流程審視。優先問題由兩個 gpt-6-luna 子代理修復；此處只記下一輪優化研究，不將尚未跑過的模型或新設定當成效能成果。

## 1. 第一優先：讓已驗證的加速路徑真的進入整合流程

### 獨立實驗與 Echo-Stream 的建構參數不同

本機呼叫證據：

- `../TestSeparateTTSSystem/Entry.py` 的 shell／profile 預設 `use_accel=True`。
- `../TestSeparateTTSSystem/echo_tts/runtime/indextts_backend.py` 類別預設 `use_accel=False`，並將參數傳入引擎。
- `../TestSeparateTTSSystem/echo_tts/modules/tts_module/lite_engine.py` 將 `self.use_accel` 傳給 GPT；`gpt/model_v2.py` 依此建立 AccelInferenceEngine。
- 本輪開始時，Echo-Stream `_build_backend()` 未傳該參數。因此標準建構路徑實際選擇關閉；這是程式接線結論，不是對既有執行中程序的檢查。

TTS 專案 8 月 19 日 PM「2.5 加速疊加實測定案」已明確提醒此預設差異。其舊測試（91 字中文、含冷啟、repeat 2）記錄 GPT 11.472→2.269 秒、首音 5.628→2.827 秒。不能將倍率直接套到目前短句、情緒、GPU 共用或 Web 延遲。

**實作方向**：將 use_accel 變成明確的 adapter／啟動設定，記錄 requested、實際生效後端與 fallback 原因；先用 factory kwargs 測試保證接線，再安排受控的真實整合驗證。不要默默 fallback 後仍顯示「加速開啟」。

**與其他工作的依賴**：先解決模型重入；具有共用 KV／CUDA Graph 狀態的加速器更不能讓兩條 stream 同時進入。

## 2. 自然度的第一個低成本調查：串流與完整 WAV 並不等價

`lite_engine.py` 的 callback 在每段 trim／fade 後立即送出（約 1957 行），而 `_dyn_silence_ms` 是在所有 callback 後、拼接完整 WAV 時加入（約 1964 行）。預設間隔由 `interval_silence_ms` 決定，預設 200 ms，可受 dynamics 改寫。

Echo-Stream 消費 callback PCM，不使用最終 WAV，adapter 另加預設 15 ms 靜音與 4 ms 淡化；前端再加約 6 ms fade。這些效果並不等同完整 WAV 的韻律間隔。

因此，**若先前聽感是聽落地 WAV，不能直接代表整合串流的自然度**。獨立 CLI 也可能走 callback，應按實際播放模式辨識，不假設全部 CLI 都等於完整 WAV。

研究順序：

1. 選既有多段語料，核對 callback 音訊與最終 WAV 的停頓來源。
2. 定義單一停頓責任：模型本身、語意切點與傳輸拼接各自負責什麼，避免多處疊加或漏掉。
3. 再決定句末、逗號、延續片段所需間隔。不能為對齊 WAV 一律補 200 ms，否則可能加重卡頓。

這個方向不需要更換模型，也不應先改情緒強度來掩蓋傳輸差異。

## 3. 播放剩餘量驅動切分：同時改善等待與韻律

目前 splitter 只看文字權重，不知道播放端還有幾秒。可在新的播放回報可用後研究：

- 起始 buffer 空：於最早的安全語意邊界提交，限制首段等待。
- buffer 充足：等待較完整的語句，減少獨立合成與語調重啟。
- buffer 接近耗盡：使用已完成的安全邊界，提前送出下一段。
- 不能為了湊長度等待未知的未來 token；需最長等待時間、工具等待 flush 與取消規則。

概念條件：下一段的「剩餘文字等待＋預估合成時間＋傳輸餘裕」應小於已排程可播放時間。估計需依語言、加速模式與句長更新；最壞情況與平均值分開。

用既有 token 到達時序與 chunk 時長重播即可先評估排程，無須重新問 LLM。只是播放不斷仍不代表韻律自然；需保留人工聽感比較。

## 4. S2Mel 的研究方向是固定形狀與編譯快取，不是重開 compile

舊 PM 記錄：在 RTX 5070 Ti／sm_120、當時工具鏈下，同 shape warm 的 CFM estimator 1678→1163 ms，但變動文本觸發 stride 重編譯，出現 15–40 秒成本。因此 `compile_s2mel` 已定案關閉。現在的本機 config 也仍關閉。

本輪還看到引擎用 CUDA synchronize 校正階段計時的註解：早期曾將上游工作算進 BigVGAN，造成約 0.2 秒純計算被記為約 4 秒。舊 PM 階段占比不能直接當現在瓶頸分布。

可借鑑 Breeze 的 shape bucket 與預先暖機方式，但要驗證：

- 不同 text／mel 長度與 stride 是否落到有限 graph 集合；超出範圍走已知 eager fallback。
- padding、attention mask、輸出裁切是否改變流模型的有效條件與音質。
- graph pool 額外顯存是否擠壓 STT；不能只量 TTS 單獨最快時的數字。
- 生產路徑與 profiling 路徑的同步點分開評估。不能直接刪同步後拿不正確的 CUDA 計時宣稱加速。

這是在 TTS 子專案內做的研究，不把 torch／模型邏輯搬進 Echo-Stream core。

## 5. Breeze TTS 2：最值得借用的三件事

[官方快路徑](https://github.com/breezeblue-ai/breeze-tts#-fast-inference-options) 將 text encoder、prefill、decode、depth decoder 與 codec 分開控制，採用 shape bucket、固定 cache 與逐幀解碼。對本專案可借用的是：

1. **分階段啟用與回退**：每個加速選項都能單獨識別效果與異常。
2. **語意內容與傳輸小塊分離**：在同次生成內持續輸出音訊，不必每個傳輸塊重開一個句子。
3. **風格指令與聲線並存**：利用現有 SpeechStyle.style，不另造重複的風格資料模型；非語言事件則需明確結構與能力宣告。

其 [API](https://github.com/breezeblue-ai/breeze-tts/blob/main/breeze_infer/api.py) 以單一請求鎖保護共享 runtime，並使用完整 text form 與 PCM 串流輸出。這也提醒：audio-out streaming 不等於 text-in streaming，不能假設能對同次生成追加任意 LLM token。

本機目前沒有 Breeze 音質、聲線與首音驗證。官方 H100 的結果只用來辨識技術，不作本機承諾。

## 6. AuK／AuK-Flash：適合方法研究，短期不放進首音路徑

[AuK 報告](https://arxiv.org/html/2609.08936v1) 用 consistency 初始化與分任務蒸餾取得四步免 CFG 的學生模型。價值在於將多步、雙分支引導的成本提前吸收到訓練，而不是在推理時任意降低步數。

需留意 [官方執行說明](https://github.com/Tencent-Hunyuan/AuK)：

- 語音生成需要文字／音訊 encoder 與 VAE，不能只計算 1.5B 主模型。
- 提供目標時長或由文字估時；若要借用，需檢查短句與時長錯估是否影響內容完整性。
- 官方 Prompt Enhancer 會使用 LLM，若接在既有 LLM 之後會再增加一輪等待；即時路徑應先用確定性的任務模板。
- 官方 A800 測得的完整推理顯存需求與 CPU offload 方案，不等同本機容量或速度；offload 節省顯存也可能增加首音延遲。

優先研究其「內容、聲線、表達」的控制分離、編輯任務訓練與少步數蒸餾。若未驗證原生早期音訊輸出，將它串成回答後製會讓首音必須等待額外模型，與當前目標衝突。

## 7. 端到端尚可重疊的工作

| 候選 | 可節省什麼 | 前提與代價 |
| --- | --- | --- |
| 穩定 partial 上預取記憶 | 最終輸入後的必要檢索等待 | generation 失效、內容變動時丟棄；不自動寫入記憶 |
| 根據部分轉錄預先組裝靜態 prompt | CPU 組裝時間 | 不等同提前請求 LLM，先看是否值得 |
| 語意判停 | 固定靜音等待 | 需讀現有 STT／判停實驗；與誤切率一起驗收 |
| TTS 角色 conditioning 快取 | 重複前處理 | 本機已有角色特徵與 emo_indices，先避免重做已有 cache |
| callback-only 合成出口 | 每句末尾拼接／存 WAV 的成本 | 主要改善下一句排程；callback 已先送出，不能宣稱首 chunk 同幅改善 |
| 依播放水位排 TTS／STT | 共享 GPU 的尾端延遲 | 不能簡單讓 STT 等整輪 TTS；需細顆粒工作邊界 |

目前不優先做 speculative LLM／TTS：partial 尚未定案、回收成本與模型不可段內取消，可能浪費 GPU／token 並讓真正回答更慢。先修取消與排程，再討論可受控的預先推理。

## 建議選擇

短期收益最可驗證的是 **加速參數接線、callback／WAV 停頓一致性、播放水位驅動的切分**。中期再研究 **S2Mel 有限形狀編譯快取**與 **Breeze 原生音訊串流的獨立 adapter**。AuK-Flash 的蒸餾屬較長期模型工作，不以額外後製方式增加當前回答路徑。

所有項目以端到端首個實質回答、斷流時間、插話停止時間與盲聽自然度一起判斷；不靠 filler 首音或單一 RTF 決定採用。

## 下一輪最小比較設計

先沿用同一批中英混合、短句、長句與情緒切換語料；固定聲線、文字到達時序及採樣設定。每次只改一項，區分冷啟、暖機與 STT 同時工作。

| 比較 | 主要觀測 | 採用條件 |
| --- | --- | --- |
| use_accel 關／開 | 實際後端、首 callback、生成結束、首個實質回答播放時間 | 實際進入加速路徑；端到端改善且無漏字、情緒或角色退化 |
| callback／最終 WAV | 各段有效發聲、靜音位置、拼接處盲聽 | 先證明差異來自哪一層，再調整停頓責任 |
| 固定切句／播放水位切句 | 每次等待文字時間、模型等待時間、播放斷流總長、切點 | 降低斷流且首音沒有明顯倒退；韻律盲聽通過 |

瀏覽器回報的是播放時鐘進度，仍不代表喇叭實際出聲時間；音效裝置輸出延遲需另列。伺服器與瀏覽器時鐘不可直接相減，跨端事件先以同端相對時間及 generation 對齊。若目前紀錄缺少逐 token／逐 chunk 時序，先補量測，再用紀錄重播驗證排程。
