四份平行調查的結論彙整。**只記會改變我們決策的部分**，完整報告在對話記錄裡。

## 一、SentenceSplitter 是不是正確的路？—— 是

**結論：句子級切分就是串接式管線的正解。可優化的是切點怎麼選，不是要不要切。**

CosyVoice 2/3、Orpheus、FlashTTS 能做到 150-325ms 首包、「不等句子邊界」，
靠的是**模型架構層級的能力，不是推論期的 wrapper**：

| 方案 | 機制 | 首包延遲 | 能否移植 |
|------|------|---------|---------|
| CosyVoice 2 | text/speech token 訓練時就按 ~5:15 交錯排列（interleaved LM）+ chunk-aware causal flow matching | 150ms | ❌ 要改模型 |
| CosyVoice 3 | 串流架構沿用 2 代，只換 tokenizer / 擴數據 / 0.5B→1.5B | 同上 | ❌ 不影響判斷 |
| Orpheus | SNAC-frame-level 逐 token 解碼，需維持 83-91 tokens/s | ~200ms | ❌ 要改模型 |
| FlashTTS | lagged multi-track + MTP + 2-NFE mean flow；首 chunk 24 token、之後 18-token hop + 6-token lookahead | **325ms**（不是 130ms，數字更正） | ❌ 要改模型 |
| F5-TTS / XTTS | 官方推薦做法就是句子級 chunk streaming | 320ms（XTTS 首 chunk） | ✅ 與我們同路線 |

IndexTTS 2.5 是「先生成完整 semantic token 序列 → DiT + vocoder」，
沒有交錯生成的訓練基礎。換模型會丟掉情感向量系統這個既有資產。

連專門研究更細切法的 Prosodic Boundary-Aware Streaming 論文，結論也是
**「智能切分」而非「完全不切」**。

### 可移植的工程技術

| 優先 | 技術 | 效益 | 成本 |
|------|------|------|------|
| 1 | **TensorRT-LLM 加速 IndexTTS-2**（Faster IndexTTS-2, [arXiv:2607.21042](https://arxiv.org/html/2607.21042v1)）| GPT 元件 4.8-5.0×、端到端 3.46-3.60×；論文數字 ~600ms(2s chunk) / ~400ms(1s chunk) | 中高，但**是同一個模型**，CP 值最高 |
| 2 | **Hann window cross-fade + 段間短靜音墊** | 消除拼接爆音；UTMOS 損失可壓在 -0.08~-0.13 | 低，純訊號處理 |
| 3 | 只在非發聲區（詞間短靜音）切分 | 大幅降低喀嚓聲/呼吸聲假影 | 低 |
| 4 | Fish-Speech S2 的 RadixAttention prefix caching（命中率 86.4%）| 固定音色場景可能吃到紅利 | 高，需先驗證 IndexTTS GPT 部分能否跑在 SGLang/vLLM |

**分段合成的品質影響**：對音色/speaker identity（SIM-o）幾乎無影響，
對韻律自然度（UTMOS）輕微下降，chunk 越小越明顯。

⚠️ **推測但值得注意**：情感向量應該按「整段回應」統一決定，只有音訊層面
才逐段合成。若每個分段獨立決定情感參數，段間情感跳變會在銜接處被放大感知。

## 二、turn boundary 與 barge-in

### 兩者必須是分開的 Protocol

錯誤代價不對稱：turn-end 判太慢 → 使用者乾等（要**靈敏**）；
barge-in 判太浮動 → 一聲咳嗽就打斷（要**保守**）。合併就只能取一組閾值。

LiveKit 把 `turn_handling` 與 `min_interruption_duration` 分開配置、
Pipecat 把 Smart Turn 模型與 `TurnAnalyzerUserTurnStopStrategy` 分開，
是同一個結論的兩種實作。**已採用。**

### 純 VAD 靜音判定的結構性矛盾

閾值短 → 思考停頓被誤判為講完；閾值長 → 反應遲鈍。**調參數解不掉。**
業界一致的解法是「VAD 決定何時檢查，語意模型決定是否真的結束」+
動態延展等待視窗。所以 `TurnDecision` 回傳信心分數 + 建議等待時間而非 bool。

| 方案 | 架構 | 參數 |
|------|------|------|
| LiveKit turn-detector | Silero VAD + 135M transformer（SmolLM v2 微調），CPU，<500MB RAM | `min_endpointing_delay=0.15s`、`max_endpointing_delay=1.2s`、`min_interruption_duration=0.5s` |
| **Pipecat Smart Turn v3** | Silero VAD(`stop_secs=0.2`) 觸發後分析原始波形 | **8MB 量化、CPU 推論 12ms**、MIT 授權 |
| OpenAI `server_vad` | 純閾值 | `threshold=0.5`、`prefix_padding_ms=300`、`silence_duration_ms=500` |
| OpenAI `semantic_vad` | 語意分類器動態決定等待 | `eagerness`: low/medium/high/auto |

**升級路徑**：Phase 0 固定閾值 → Phase 1-2 接 Smart Turn v3（最輕量、
本來就設計成搭配 Silero 用、與既有雙 VAD 架構相容度最高）→ Phase 3+
視實測 false-interruption 率再考慮 LiveKit 135M。

生產標準參考：turn-taking gap 200-400ms、false barge-in rate < 2%、
TTS flush < 60ms。但那是有語意模型撐著的數字，Phase 0 純 VAD 版用 700ms。

### barge-in 善後：只存使用者實際聽到的部分

Azure Voice Live API 的 `auto_truncate` 就是做這件事，理由是
「否則 LLM 會誤以為自己講了使用者從未聽到的內容」。

⚠️ **Pipecat issue #4111 的教訓**：TTS 播放與 context aggregator 的 frame
排序問題，導致 context 在 TTS 完整輸出前就被提交。
**我們的 `PipelineRunner` 已經把 commit 嚴格排在「確認實際播出量」之後。**

⚠️ **LiveKit issue #3515**：`min_interruption_words` 會**覆蓋**
`min_interruption_duration` 而非疊加。我們明確定義成 AND 避開這個坑。

### addressee detection（Discord 多人）沒有現成方案

學術上至今是開放問題，商用系統普遍退回 wake-word。所以
`AddressingClassifier` 介面現在就留好，Phase 5 用 wake-word/名字偵測 +
語者識別當務實起點，別期待接一個 library 就解決。

## 三、ThinkStage：首句一致性問題的正解

### ⚠️ 假設被推翻：LLM 串流生成到一半**無法**改 context

Gemini / Ollama / vLLM 全都是「一次 prefill + 自迴歸 decode」。KV cache
一旦建立無法替換已編碼的前綴。**這是 Transformer 自迴歸推論的結構性限制，
不是產品限制，沒有任何一家支援。**

所以原本設想的「late-context 注入」不成立。

### 正解：首句改用固定 filler，從源頭排除矛盾

業界的 filler 是**完全不含實質內容的固定短語**（「嗯」「讓我想想」），
不是「LLM 自由生成、可能包含記憶斷言的一整句話」。

我們原本讓 LLM 在無記憶 context 下自由生成首句，那才是矛盾的根源——
**平行跑這個時機決策是對的，缺的是首句生成內容的邊界控制。**

| 排序 | 方案 | 成本 | 體感代價 |
|------|------|------|---------|
| ① | **首句固定 filler，不含可反駁斷言**；retrieve 完成後把 filler 當 assistant 前綴、開新請求續寫 | 低（只改 prompt 策略）| 低，**直接消除**副作用 |
| ② | speculative retrieval（partial transcript 先查）| 中 | 低，記憶追上首句 |
| ③ | 強制等記憶，用音效頂住 | 低 | 中，仍有停頓 |
| ④ | 讓矛盾發生、後續帶過 | 極低 | **高**，使用者感知「說謊被抓包」 |

注意：「我不記得了」是斷言，**不能**當 filler；「讓我想一下」才安全。

filler 業界實務：即時 TTS 合成 > 預錄（預錄重複播會顯機械），
搭配固定文字庫隨機挑選。**只在確定會有延遲時才用**，否則顯得笨。

### Memory retrieve 的 1-3s 很可疑

bge-m3 單次 query embedding 在合理硬體上只要 **5-10ms**。
1-3s **不是 embedding 推論的瓶頸**。可疑處：

1. EcphoryRAG 的 NetworkX 圖遍歷（Python 原生圖庫在大圖上慢）
2. 神經化學調控是否每次 retrieve 都重算
3. 三層記憶是否序列化查詢而非平行

**先 profiling 找瓶頸，再決定優化手段**，否則可能在優化錯的地方。

加速手段（依序）：query embedding 快取 → ONNX + INT8（約 3×）→
ANN index (HNSW) → rerank 只對 top-K。

### LLM TTFT

- **Gemini context caching**：implicit（自動）/ explicit（保證命中）。
  explicit read ~$0.20/1M（vs 原價 $2/1M Pro），write ~$0.50/1M，
  **另計每小時儲存費**。⚠️ 這主要是**成本優化**，官方沒給「cache hit 對
  TTFT 省多少 ms」的數字，不能假設等同 vLLM 的加速幅度。
- **Ollama**：CPU backend 完全不重用 KV cache（[issue #14780](https://github.com/ollama/ollama/issues/14780)，實錘），
  GPU 正常。**驗證方法**：看 prompt processing 時間是否隨輪次遞減
  （實測案例：冷 962ms vs 熱 54ms，17.7×），查 `prompt_eval_count` 沒用。
  ⚠️ **若曾在 CPU backend 上測過延遲數字，那些數字不可信。**
- **vLLM `enable_prefix_caching`**：長 prompt 高重用可達 2×-7× TTFT
  （4.3s→0.6s），但低命中率場景反而因 hash 開銷變差。
- **speculative decoding 對 TTFT 幫助有限**——它作用在 decode 階段，
  prefill 才決定 TTFT。DuoDecoding 甚至顯示對 TTFT 有 1.5-1.7× 額外開銷。

## 四、InputStage 與 AEC

### ⚠️ STT 400ms 預算不切實際 → 改為 700ms

400ms 是**雲端專用串流 ASR** 的量級（AssemblyAI Universal-3 Pro P50 ~150ms、
第三方測 mean 262ms / p95 355ms；Deepgram Flux 端點偵測 <300ms）。

Whisper 系是 encoder-decoder attention 架構，即使 turbo + int8 也先天不利。
現況「VAD 判定結束後才整段轉錄」是 1-2s；改造成增量串流 +
LocalAgreement 後社群實測 **500-800ms**。

**partial transcript 的用法**：可以觸發「輕量、可丟棄」的下游動作
（memory retrieve 預抓、UI 提示），**不建議直接餵 LLM prefill**——
LocalAgreement 修正雖少，一旦發生會讓已 prefill 的 context 失效。
要接下游 prefill 前，先做一次「partial 修正率」實測。

**large-v3-turbo 選型正確**（809M、decoder 4 層、約 large-v3 的 6 倍速、
WER 只增 0.3-0.7 個百分點），不需要換 distil 系列——distil 的優勢在
batch 吞吐量，對單串流低延遲沒有明顯好處。

### ✅ Discord 不需要 AEC（前一輪點名的風險，解除）

- Discord voice receive 是**逐使用者的獨立 Opus/PCM 流**（透過 SSRC 路由），
  **天然語者分離**
- Discord 語音伺服器不會把音訊送回發送者自己，**bot 的 TTS 輸出不會出現在
  bot 自己的接收流裡**——架構上就沒有 loopback 路徑

推論：**Discord 場景 bot 端不需要自建 AEC**，且 **pyannote diarization
在 Discord 場景可能是多餘的**，值得重新評估是否要為它付延遲成本。

### 本機喇叭外放場景才需要處理

| 方案 | 成本 | 代價 |
|------|------|------|
| headset（物理隔離）| 零 | 無 |
| TTS 播放期間動態調高 VAD 閾值 | 低，**不需 reference signal 對齊** | 無法 double-talk，依環境手動調參 |
| half-duplex（播放時關 STT）| 最低 | **犧牲 barge-in** |
| WebRTC APM 真 AEC | 高 | 需 reference signal + 延遲估計 + 取樣率對齊；⚠️ **win32 建置可行性未知** |

Python 綁定候選：`pywebrtc-audio`（pybind11，~2µs/10ms frame，2026-05 仍維護）、
`aec-audio-processing`（有 `set_stream_delay`）。SpeexDSP 對非線性回音
（喇叭失真、房間反射）建模能力有限。

### 重採樣：soxr 最快

| 方案 | 48k→44.1k (10s) |
|------|----------------|
| **soxr** | ~1.16-10.8ms |
| torchaudio（預算 kernel）| ~10-13.8ms |
| scipy.signal.resample | ~2.42-21.3ms |
| resampy (kaiser_fast) | ~10.5-108ms |

⚠️ soxr HQ 在 44.1k↔48k 有約 **1000 output samples（~20ms）的固有演算法延遲**，
要納入 TTFA 預算。若管線已有 GPU tensor 常駐，用 torchaudio 可省一個依賴。

**重採樣放 Frontend Adapter 是對的**：Pipeline 核心只處理統一取樣率
（16kHz in / 22.05kHz out），Adapter 負責跟外部世界對接。
